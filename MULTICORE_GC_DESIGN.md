# Embedded managed multicore: audit and design decision

Status: design approved for staged work, 2026-11-03. No multicore managed execution is enabled yet. Line references below refer to the audited checkout; the compiler and target modules are separate repositories.

## Decision

Start with a two-mutator, non-moving, precise stop-the-world (STW) collector. Each managed execution context has its own root and exception frames. Collection begins only after every registered mutator has acknowledged an epoch and parked at a compiler-defined safepoint, or has entered a rigorously defined native-safe state with no unregistered managed references. Keep heap mutation under one short-lived allocator lock at first, release it before requesting a collection, and run tracing/sweep exclusively while all mutators are parked. No arbitrary native task may call managed code. A coarse lock around *all* managed execution would serialize the feature and still fail to define root capture, callbacks and blocking semantics.

This is a **go** for Stage 0 tests and a narrow Stage 1 prototype only. It is **no-go** for a public parallel managed API until the gates at the end pass on both targets.

A multicore design must execute finalizers after releasing the STW state, with objects held alive across that transition. | ESP32 | `esp32.mod/runtime.mod/native/esp32_runtime.c:36-67,77-104` binds one CPU-0 FreeRTOS task on first arena acquisition, rejects ISR, other cores and other tasks, and gates native callbacks to that owner. Wi-Fi/timer/UART callbacks and deferred events use native queues/locks (`esp32.mod/runtime.mod/native/esp32_events.c`, `esp32.mod/network.mod/wifi.mod/native/esp32_wifi.c`). | Build and tests | `bmk_src/bmk_pico.bmx`, `bmk_src/bmk_esp32.bmx` generate target CMake/SDK builds; `bmk_embedded_board.bmx` selects boards/architecture. No multicore option is wired through bmk. Existing compiler IR tests (`bcc2/tests/test_compiler_ir.bmx:336,397-436,549-585,667-683`) check root emission. `embedded.mod/tests/embedded_runtime_conformance.c`, `embedded_gc_sweep_conformance.c` and `benchmarks/gc` cover single-core correctness/performance, including fragmentation; none proves concurrent safety. |
| Desktop runtime | `brl.mod/blitz.mod/blitz_gc.c` uses Boehm and has desktop thread registration. It is a distinct collector and ABI; its registration functions are not portable evidence for this precise embedded heap. |

The checked runtime has no managed thread registration, no cooperative poll, no barrier, and no managed synchronization contract. Existing target locks protect native queues, not the collector. Inspect and preserve all existing native callback gates during integration.

## Non-negotiable invariants

1. A tracing or sweeping pass observes a stable set of managed roots and a stable heap graph, or a proven barrier maintains the chosen tri-colour invariant. No live object is reclaimed.
2. Each executing managed task owns exactly one registered context; only its task may push/pop its frames. Context publication/removal and root-table edits are synchronized with collection. The collector never treats two ESP32 tasks on one core as one context.
3. No other mutator sees an allocation before its header, type, pointer fields and mandatory sentinel/zero initialization are valid. Application publication requires release/acquire or an equivalent lock. Constructors may publish `Self`, so language-level fully initialized semantics cannot be assumed without further restrictions.
4. No managed value survives across a native transition solely in an unrecorded C local/register. A native-safe blocked task has explicit stable roots, or remains a mutator that must rendezvous before collection.
5. Heap header list, free list, bump offset, mark epoch/queue, root token table, finalizer state and statistics have one writer or a documented synchronization rule. Interrupts never allocate, collect or execute managed callbacks.
6. Finalizers run at most once outside allocator/handshake locks, can resurrect, and are not allowed to invalidate a suspended mutator's snapshot. Exceptions unwind only the current task's frames. Shutdown waits for registered tasks to exit before releasing any arena.

## Strategy comparison

| Strategy | Correctness work | RAM/flash and pause consequences | Decision |
| --- | --- | --- | --- |
| One global managed-execution lock, STW collection | Simple baseline for serialized tasks; still needs task-local roots and native transitions. | Low metadata, but no simultaneous managed execution; a blocked holder stalls all work. | Useful diagnostic baseline, not final architecture. |
| Cooperative STW precise mark/sweep | Registered contexts, poll/park protocol, stable roots, short allocator lock. No write barrier while parked. | One descriptor plus stack per worker; pause includes rendezvous + whole trace/sweep, proportional to live graph and heap. | Recommended first parallel architecture. |
| Forced core/task suspension | Must capture compiler roots at arbitrary program counters and avoid suspending while holding heap/SDK locks. | Potentially shorter rendezvous, high target-specific fragility; Pico lockout consumes FIFO IRQ and ESP32 cross-core stall has restrictions. | Reject as general root-capture mechanism. |
| Incremental mark/sweep with STW root snapshot | SATB or incremental-update barrier on **every** pointer store, deletion/array/Struct copy, plus remark and safe sweep. | Barrier traffic, worklist/card storage and overflow handling; snapshot still pauses; fragmentation persists. | Stage 4 only after measurements. |
| Fully concurrent or parallel mark | Mutator barriers, atomic colours/work queues, allocation colour, weak/finalizer protocol, safe reclamation epochs. | Highest RAM/flash and proof burden; still needs root handshakes and likely short pauses. Parallel marking on two small cores may contend on memory. | No present justification. |
| Moving collector | Precise roots help, but every native pin, DMA buffer, callback handle and interior pointer needs an update/pinning rule. | Compaction improves fragmentation but raises pause, metadata and native ABI cost. | Out of initial scope. |
| Per-core allocation regions/caches | Ownership/transfer, flushing at collection, cross-core free and fragmentation policy. | Better fast path if contention measured; reserves memory that may be unusable by other core. | Stage 3 experiment. |

MicroPython is a useful comparison, not a template: its docs identify thread stacks and registered C roots, its ESP32 port uses FreeRTOS tasks with a GIL, and its state includes a GC mutex for GIL-free configurations. It conservatively scans stacks, whereas this runtime deliberately has typed compiler roots. [MicroPython memory model](https://github.com/micropython/micropython/blob/master/docs/develop/memorymgt.rst), [ESP32 port](https://github.com/micropython/micropython/blob/master/ports/esp32/README.md), [GC state](https://github.com/micropython/micropython/blob/master/py/mpstate.h), [RP2 threading code](https://github.com/micropython/micropython/blob/master/ports/rp2/mpthreadport.c).

## Architecture and direct answers

**Registration and roots (Q4, Q9).** Use a fixed-capacity registry keyed by a target task handle, with generation counter and states `STARTING`, `RUNNING`, `NATIVE_SAFE`, `PARKED`, `EXITING`. Pico's first prototype may bind one managed worker to core 1; ESP32 workers must be pinned or use task-local storage, never `xPortGetCoreID()` as task identity. Create through a runtime-owned trampoline: reserve stack/context, register before user code, wait for module initialization, run the managed entry with top-level exception boundary, exit through a joined teardown path. No arbitrary task registration API until native root discipline is specified. Global frames belong to runtime/module state, not the first task's frame chain. At a poll, compiler-rooted locals and frame links are stable; acknowledge the GC epoch with release semantics, then wait. Collector loads acknowledgements with acquire semantics and traces all registered frames plus root tokens/globals. Registers need no separate scan only if compiler-generated slots cover every managed value live across a poll/allocating call; test this with aggressive optimization.

**Native states (Q5).** An interrupt only records native data and signals the owner. A callback into managed code must use the runtime trampoline on a registered task. Before a blocking SDK call, a task may declare `NATIVE_SAFE` only after storing all live managed handles in registered slots and proving that native code cannot mutate the managed heap; on return it waits for any active collection before re-entering. Otherwise remain `RUNNING`, and collection waits for a poll. A call that can block indefinitely while retaining unrooted managed pointers is unsupported. Timeouts on the collector handshake fail the request safely (or panic in a diagnostic build); never sweep from a partial rendezvous. Pico multicore lockout can assist diagnostics, not precise arbitrary-PC capture. The Pico SDK documents that lockout uses the FIFO IRQ and must be initialized on the victim; ESP-IDF documents SMP spinlocks and that suspending a scheduler only affects one core. [Pico SDK multicore and synchronization](https://www.raspberrypi.com/documentation/pico-sdk/high_level.html), [ESP-IDF FreeRTOS SMP](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/system/freertos_idf.html).

**Allocation and publication (Q1, Q6, Q7).** Initially guard heap metadata operations with a target mutex/spinlock whose critical region is bounded to metadata changes; never collect, invoke initializer/finalizer, block or call SDK services while holding it. The newly allocated block remains owned by its task during zero/sentinel initialization; a collection request must make that temporary root visible before parking. Cross-core publication through a shared field/queue needs a release store and acquire load (or a lock that supplies the same happens-before relation). Plain unsynchronized shared BlitzMax fields have a data race; define a supported atomic/locked publication API before promising safe sharing. C11/GCC acquire-release atomics are the portable contract; relaxed is sufficient only for independent counters. Verify compiled primitives and lock-free width per target: RP2040 ARMv6-M may require Pico SDK spinlocks for atomic operations, RP2350 ARM/RISC-V and Xtensa differ. Never infer ordering from a volatile field, a local interrupt mask or core affinity. [Pico SDK atomic implementation note](https://www.raspberrypi.com/documentation/pico-sdk/runtime.html), [ESP-IDF SMP memory model and locks](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/system/freertos_idf.html).

**Collection and boundedness (Q2, Q3).** Useful lock-free work is per-context frame updates and private object initialization between polls; shared allocation metadata and root registry require synchronization. A truly pause-free precise design is possible in principle only with comprehensive barriers, concurrent root snapshots and reclamation protocols; it is not plausible here at acceptable initial RAM/code cost, particularly with native boundaries and no VM. Cooperative pauses can be measured and their *rendezvous timeout* bounded, but whole-heap marking/sweeping remains proportional to graph/arena size. Incremental marking could limit work per allocation after a brief root snapshot and a remark, but cannot be claimed bounded until barriers, overflow and finalizer semantics are proven. SATB logs overwritten old references; incremental update shades new edges from black objects. Either must cover generated field stores, array writes and bulk copies. Epoch/RCU ideas may protect registry removal/metadata snapshots, but cannot substitute for tracing heap references or safe reuse in a fixed arena. Metronome demonstrates that stronger real-time GC needs explicit scheduling and fragmentation control, with a much larger implementation budget. [IBM Metronome fragmentation paper](https://research.ibm.com/publications/controlling-fragmentation-and-space-consumption-in-the-metronome-a-real-time-garbage-collector-for-java).

**Other runtime semantics (Q8, Q10).** Type descriptors remain immutable after module initialization; any lazy generic/type cache must be made one-time and synchronized. During STW, select finalizer candidates and hold them live, then unpark and execute finalizers on a designated managed task without collector locks; repeat collection on allocation pressure to observe resurrection. If weak references are added later, clear them only after reachability determination and before finalizer visibility, with a documented resurrection policy. An OOM on one task throws to that task's preallocated exception boundary; another task never borrows its handler. All targets can share registry states, GC epochs, root semantics, no-ISR rule, publication contract and failure outcomes. Pico supplies core-1 launch/FIFO or semaphore wakeup/spinlocks; ESP32 supplies pinned FreeRTOS task creation, task handles/TLS, mutex/semaphore notifications and callback gate. Target adapters must report whether a board is truly dual-core and whether the configured SDK allows the feature.

**Compiler, ABI and bmk (Q11, Q12).** Add explicit `gc_poll` at loop backedges and selected calls, plus native enter/leave wrappers, while retaining existing precise slots. Check all allocation-capable expressions, constructor argument sequencing, `Super`, exception paths and Struct copies against the poll contract. Replace per-core context index with a runtime task-context accessor for ESP32. Version the embedded runtime ABI when poll/registration and publication primitives appear; compile every module with the same feature flag and reject mixed objects. Add opt-in bmk setting passed through both C compiler and target CMake/SDK configuration; exclude registry, locks, polls and worker API from ordinary single-core builds with compile-time conditionals. Compare binary size, RAM and allocation throughput against the same baseline build.

## Failure and deadlock rules

- Handshake never waits while holding allocator, root-registry, event-queue or SDK locks. A worker never parks while holding one of these locks. Establish and instrument a single lock order.
- Collection request and task start/exit serialize through registry epochs; a late task cannot begin managed code until the current collection ends. A departing task remains registered until its root frames are gone and collector acknowledges teardown.
- If a worker is in an unbounded native call, either it entered `NATIVE_SAFE` with complete roots or collection times out without reclaiming. Forced task deletion is forbidden while registered.
- A finalizer exception cannot leave collector state locked/active. A finalizer may allocate and resurrect; queue membership and at-most-once flag survive exceptions.
- Failed allocation must account for a second finalizer cycle, fragmentation despite free bytes, and inability to acquire arena/worker stack; throw/panic is task-local and deterministic under the configured policy.
- Public shared mutable Object fields need synchronization even when GC is correct. Native queues carry tokens or retained roots, never raw unprotected pointers.

## Stages, measurements and gates

| Stage | Deliverable | Go/no-go gate |
| --- | --- | --- |
| 0 | Host collector harness with deterministic interleavings, heap validation after every collection, fault injection at split/coalesce/mark/queue/finalizer/exception/arena failure; establish single-core Pico/ESP32 latency, throughput, RAM and flash baselines. | Existing compiler/runtime tests pass; root liveness under optimization verified; no unexplained heap validator failures. |
| 1 | Fixed registry, task-owned contexts, cooperative STW epoch protocol, target adapters, internal worker experiment only. | Every registered worker parks or declares native-safe; timeout never sweeps; host sanitizers and on-device handshake tests pass. No public parallel managed promise. |
| 2 | Runtime-created managed worker, cross-core atomic/locked publication, synchronized allocation, callbacks and exceptions, finalizer handoff. | Repeated concurrent Object/Array/String allocation, cycles, root churn, mutations, task create/join under pressure, native block/re-entry, interrupts, deferred callbacks and OOM fault matrix pass on dual-core ESP32 and RP2040/RP2350 hardware. Long soaks and adverse scheduled interleavings show no lost objects/deadlock. |
| 3 | Per-core allocation state only if measured lock contention warrants it. | Measured throughput improves without unacceptable stranded space, fragmentation or pause regression. |
| 4 | Prototype incremental/concurrent collector only if measured full-heap pause fails a stated product budget. | Barrier coverage audit, invariant proof, overflow tests, weak/finalizer protocol and hardware measurements justify added flash/RAM. |

Instrument collection phase times (request-to-last-ack, root scan, trace, sweep, finalizers), maximum poll gap, allocator lock hold/wait, heap free-largest-block and fragmentation, failure reason, per-task state and violations. Record percentiles and maxima under fixed arena sizes and identical workloads, including 64/256 KiB where supported. Expected initial multicore overhead: one context/registry entry and one worker stack per task, target lock/semaphore state, poll code and synchronization on every shared allocation; precise bytes and flash cost require compiled builds. Stage 1 pauses can grow with a blocked non-safe task; Stage 2 STW tracing/sweep time grows with live graph/heap. No hard-real-time, lock-free-collector or pause-free guarantee follows from this plan.

Stage 0 progress: `tests/run_gc_roots_host.py` runs optimized host stress under address/undefined-behavior sanitizers, exercising precise root churn, Object/Array/String exhaustion, and the existing sweep/finalizer/exception conformance. `BMX_EMBEDDED_GC_VALIDATE_AFTER_COLLECTION=1` enables heap validation on every collection exit, including finalizer exception escape; ordinary builds compile these checks out. The existing allocation-search host test and compiler IR test pass. Remaining Stage 0 work includes target hardware baselines, compiler liveness checks with newly emitted polls, and fault injection at collector phase boundaries. Do not push or publish a multicore API before the Stage 2 gate.
