# Stage 1 generated managed-worker device checks

Run on 2026-11-04 with an attached Pico 2 (RP2350 ARM) and ESP32-S3 (`esp32s3_n8r8`). The [fixture](../../../tests/embedded_gc_managed_worker_device.bmx) creates a managed parent containing a fixed array of two managed children. A native trampoline runs the compiler-generated BlitzMax worker on the second core/task. The worker copies the children into a fixed Array field of a local managed Struct, iterates that field, clears its original parent parameter, and polls in a nested `While` loop. The Struct root descriptor traces both children through the fixed Array. The owner removes its roots, allocates an unrooted object, and collects. The test checks that the parent and garbage are swept while both children survive solely through the worker Struct. The worker reads the second child after collection, clears the Struct fields, and releases its roots. The owner collects again and checks that the children are reclaimed. Both collections check heap integrity, and the worker exits and unregisters.

Both release builds used 64 KiB managed arenas and the `bmk makeapp -gc-multicore` path. This passed `--embedded-multicore` to bcc and the target CMake options to Pico or ESP32 automatically. The current generated worker C was inspected for four root slots (parameter, Struct, current element, and loop variable), a Struct descriptor with two managed fixed-Array elements, and polls in the fixed-array and nested wait loops. The Pico image was uploaded and verified with picotool; the ESP32 image was flashed and hash-verified with esptool, then started by watchdog reset. The earlier object-element version exposed a missing fixed-array field entry in class tracing metadata: the unreferenced second child was reclaimed while its parent survived. After fixing descriptor emission and tracing, the updated fixture passed on both devices. A sanitizer-backed [host regression](../../../tests/embedded_gc_static_field_host.c) also checks survival and reclamation of fixed object-field array elements.

The existing-local variant was rebuilt, flashed, and rerun on both boards on 2026-11-04. Pico 2 firmware was 53,556 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 191,920 bytes. Both serial monitors repeatedly reported `GC_MANAGED_WORKER,format=1,roots=pass,poll=pass,done=1` after the rerun.

The field-target variant initially reported `failed_step=5` on Pico 2: the collection after worker release still saw the objects. Generated C showed that two managed temporaries created by field reads remained in the worker root frame after the reads. The compiler now clears managed expression temporaries at statement completion in opt-in multicore builds. With that fix, the field-target variant passed on both boards. Pico 2 firmware was 53,732 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 192,096 bytes. The compiler IR suite checks that the field-read temporaries are cleared in multicore mode and that default single-core code keeps its original path.

The indexed-target variant passed on both boards after the fixture checked object and Array live counts separately. The first Pico run reported three live objects above baseline, as expected, while the fixture incorrectly expected the Array in the object count. The corrected fixture checks one additional live Array during the worker collection and its reclamation after release. Pico 2 firmware was 53,948 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 192,272 bytes. Both serial monitors repeatedly reported `GC_MANAGED_WORKER,format=1,roots=pass,poll=pass,done=1`. A final compiler rebuild after narrowing index eligibility produced byte-identical Pico UF2 and ESP32 application images to the tested builds.

The Struct-backed fixed-Array variant passed on both boards on 2026-11-04. It checks that the original parent becomes unreachable while both children remain live through only the worker's Struct root, then that both children are reclaimed after its fields are cleared. Pico 2 firmware was 53,860 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 192,320 bytes. Both serial monitors repeatedly reported `GC_MANAGED_WORKER,format=1,roots=pass,poll=pass,done=1`.

A separate default Pico build had both GC and Pico multicore CMake options `OFF` and generated no multicore C guard. The opt-in mode uses separate interface and build paths. This test covers one managed worker holding and releasing precise roots, including an interior pointer and managed elements in a field-backed fixed array. It does not establish safe worker allocation, heap mutation, arbitrary native callbacks, exception propagation, or general multicore GC correctness.
