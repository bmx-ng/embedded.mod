# Stage 1 generated managed-worker device checks

Run on 2026-11-04 with an attached Pico 2 (RP2350 ARM) and ESP32-S3 (`esp32s3_n8r8`). The [fixture](../../../tests/embedded_gc_managed_worker_device.bmx) creates an ordinary managed object containing a fixed array of two managed child objects, passes the parent to a native worker trampoline, and runs a compiler-generated BlitzMax function on the second core/task. The worker iterates the array into a field of a directly rooted local receiver, clears its original parent parameter, and polls in a nested `While` loop. Generated roots keep the receiver, fixed-array owner, and current element alive while the loop retains its interior pointer. The owner removes its roots, allocates an unrooted object, and collects. The test checks that the unrooted object is swept while the parent and both children survive. The worker then reads the second child after collection. After the worker exits the array loop, checks the retained field, and clears the field and receiver, the owner collects again and checks that all three objects are reclaimed. Both collections check heap integrity, and the worker exits and unregisters.

Both release builds used 64 KiB managed arenas and the `bmk makeapp -gc-multicore` path. This passed `--embedded-multicore` to bcc and the target CMake options to Pico or ESP32 automatically. The generated worker C was inspected for six root slots (parameter, field receiver, fixed-array owner, current element, and two field-read temporaries) and polls in the fixed-array and nested wait loops. The Pico image was uploaded and verified with picotool; the ESP32 image was flashed and hash-verified with esptool, then started by watchdog reset. The object-element version first exposed a missing fixed-array field entry in class tracing metadata: the unreferenced second child was reclaimed while its parent survived. After fixing descriptor emission and tracing, the updated fixture passed on both devices. A sanitizer-backed [host regression](../../../tests/embedded_gc_static_field_host.c) also checks survival and reclamation of fixed object-field array elements.

The existing-local variant was rebuilt, flashed, and rerun on both boards on 2026-11-04. Pico 2 firmware was 53,556 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 191,920 bytes. Both serial monitors repeatedly reported `GC_MANAGED_WORKER,format=1,roots=pass,poll=pass,done=1` after the rerun.

The field-target variant initially reported `failed_step=5` on Pico 2: the collection after worker release still saw the objects. Generated C showed that two managed temporaries created by field reads remained in the worker root frame after the reads. The compiler now clears managed expression temporaries at statement completion in opt-in multicore builds. With that fix, the field-target variant passed on both boards. Pico 2 firmware was 53,732 bytes with 14,052 bytes of application/SDK RAM; the ESP32-S3 application image was 192,096 bytes. The compiler IR suite checks that the field-read temporaries are cleared in multicore mode and that default single-core code keeps its original path.

A separate default Pico build had both GC and Pico multicore CMake options `OFF` and generated no multicore C guard. The opt-in mode uses separate interface and build paths. This test covers one managed worker holding and releasing precise roots, including an interior pointer and managed elements in a field-backed fixed array. It does not establish safe worker allocation, heap mutation, arbitrary native callbacks, exception propagation, or general multicore GC correctness.
