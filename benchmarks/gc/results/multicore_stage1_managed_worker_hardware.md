# Stage 1 generated managed-worker device checks

Run on 2026-11-04 with an attached Pico 2 (RP2350 ARM) and ESP32-S3 (`esp32s3_n8r8`). The [fixture](../../../tests/embedded_gc_managed_worker_device.bmx) creates an ordinary managed object containing a fixed array of two managed child objects, passes the parent to a native worker trampoline, and runs a compiler-generated BlitzMax function on the second core/task. The worker iterates the array, clears its original parent parameter, and polls in a nested `While` loop. Generated roots keep the parent, current element, and loop variable alive while the loop retains its interior pointer. The owner removes its roots, allocates an unrooted object, and collects. The test checks that the unrooted object is swept while the parent and both children survive. The worker then reads the second child after collection. After the worker exits the array loop and releases its roots, the owner collects again and checks that all three objects are reclaimed. Both collections check heap integrity, and the worker exits and unregisters.

Both release builds used 64 KiB managed arenas and the new `bmk makeapp -gc-multicore` path. This passed `--embedded-multicore` to bcc and the target CMake options to Pico or ESP32 automatically. The generated worker C was inspected for four root slots and polls in the fixed-array and nested wait loops. The Pico image was uploaded and verified with picotool; the ESP32 image was flashed and hash-verified with esptool, then started by watchdog reset. The object-element version first exposed a missing fixed-array field entry in class tracing metadata: the unreferenced second child was reclaimed while its parent survived. After fixing descriptor emission and tracing, the updated fixture passed on both devices. A sanitizer-backed [host regression](../../../tests/embedded_gc_static_field_host.c) also checks survival and reclamation of fixed object-field array elements.

A separate default Pico build had both GC and Pico multicore CMake options `OFF` and generated no multicore C guard. The opt-in mode uses separate interface and build paths. This test covers one managed worker holding and releasing precise roots, including an interior pointer and managed elements in a field-backed fixed array. It does not establish safe worker allocation, heap mutation, arbitrary native callbacks, exception propagation, or general multicore GC correctness.
