# Multicore native blocking boundary audit

The opt-in collector can trace a worker during a native block only when its live managed values remain in registered root frames and the native call does not touch managed memory. `enter_native_safe` publishes that state; `leave_native_safe` waits until any active collection ends before managed execution resumes. The owner is still the only collector.

| Boundary | Current treatment in opt-in builds |
| --- | --- |
| `SleepMicroseconds`, `SleepMilliseconds`, and legacy `Delay`/`MicroDelay` | A registered worker enters native-safe before sleeping and leaves afterward. Zero-duration calls keep their existing path. |
| Native event wait (`bmx_embedded_system_wait`) | A registered worker enters native-safe around the wait. Event queues and wake signals are native data. A managed-worker overlap regression passed on Pico 2 and ESP32-S3. |
| UART readable-within, put-byte, and TX-drain waits | A registered worker enters native-safe around these scalar-only calls. |
| Pico and ESP32 UART, I2C, and SPI buffer transfers | The blocking low-level calls enter native-safe only when every buffer is outside the managed arena or within a live `MemAlloc` payload. Array-backed and unrecognized arena pointers keep the worker running, so collection waits for the call to finish. The caller keeps each buffer allocated through the call; an array pointer also requires a live array reference. Timed UART reads passed the Pico 2 and ESP32-S3 device overlap regressions. |
| Pico and ESP32 stdio read/write | Enter native-safe only for a caller-owned buffer outside the managed arena or inside a live `MemAlloc` allocation. Managed array buffers keep the worker running. Buffer-free flush enters native-safe. A blocking Pico USB stdio read passed a device overlap check. |
| ESP32 filesystem read/write | An already-open native file handle may read or write through a stable caller-owned buffer while the worker is native-safe. Opening, closing, path operations and the handle lifetime remain owner-managed. The opt-in storage example compiles; device overlap is not yet measured. |
| Pico LittleFS | Owner-only: flash access rejects core 1, and file lifecycle uses owner-only manual allocation. No worker native-safe transition is added. |
| ESP32 `Pub.Net` TCP `recv_`/`send_` | In opt-in builds, these calls enter native-safe only for a buffer outside the managed arena or within a live `MemAlloc` payload. The socket handle and buffer must stay open and allocated until the call returns; array-backed buffers keep the worker running and require a live array reference. A blocking TCP receive passed an ESP32-S3 device overlap regression. |
| Other `Pub.Net` socket calls and Pico sockets | **Not yet certified for managed workers.** ESP32 `accept`, `select`, `sendto`, and `recvfrom` also block or use caller-owned buffers; each needs its own lifetime and buffer review. Pico sockets use shared raw lwIP state and callbacks, and socket creation/close use owner-only allocation. |
| ESP32 OTA write and finish | **Owner task only for now.** The update handle is allocated through the embedded allocator, flash operations can affect both cores, and the current API includes an array overload. A stable `Byte Ptr` alone is insufficient evidence for concurrent collection during flash writes. |
| Target power sleep and other SDK calls | **Not yet certified for managed workers.** These need separate target-specific review because they may affect both cores or SDK task state. |

The managed-worker device regression now holds an Object, Array and String across three 200 ms worker blocks (`SleepMicroseconds`, `SleepMilliseconds`, `Delay`). The owner waits 20 ms, then requires a completed collection while those values are still worker-rooted. It checks the live values after the block, joins, and checks reclamation. This covers the compiler-generated root frame across the native call as well as the runtime state transition. The C host suite separately checks native-safe re-entry during an active stop.

On 2026-11-04, the release `-gc-multicore` regression passed 100 worker jobs on the attached [Pico 2](multicore_native_boundary_pico2.log) and [ESP32-S3](multicore_native_boundary_esp32s3.log), including all three sleep paths and a completed collection for every job. Both ordinary single-core time-conformance images also compiled. The host GC suite passed under AddressSanitizer and UndefinedBehaviorSanitizer. Scalar UART waits compiled on both targets; they still need direct device overlap checks.

The host suite now checks stable raw `MemAlloc` ranges, stack buffers, rejected managed-object and array pointers, and rejection of out-of-bounds ranges. It also checks collection while a worker remains native-safe with a raw allocation. This is a bounded audit of the listed calls, not a promise that arbitrary SDK or pointer-based calls are safe from a managed worker. Other socket calls, OTA and SDK waits still need separate review.

The [Pico 2](multicore_native_boundary_pico2_uart_buffer.log) and [ESP32-S3](multicore_native_boundary_esp32s3_uart_buffer.log) buffer regressions used a 4 KiB `MemAlloc` destination in a 400 ms UART read on controller 1. The owner requested collection after 20 ms and completed it within 300 ms while the read was still in progress. Both devices reported `GC_STAGE2_UART_BUFFER,raw=pass,collection=pass,done=1`.

The [Pico 2 USB stdio regression](multicore_native_boundary_pico2_stdio_buffer.log) kept a worker in a one-byte read into `MemAlloc` memory while the owner collected. A host byte released the worker afterward. The ESP32-S3 console returned zero immediately when no input was available, so that console could not supply a blocking-read overlap check; its stdio path remains build-verified only.

The [native event-wait fixture](../../../tests/embedded_gc_stage2_native_event_wait_device.bmx) keeps a generated BlitzMax worker waiting with a live Object, Array and dynamically allocated String. After 20 ms the owner collects and requires completion within 300 ms, then wakes and joins the worker and verifies all three values. The current release images passed on [Pico 2](multicore_native_boundary_pico2_event_wait.log) and [ESP32-S3](multicore_native_boundary_esp32s3_event_wait.log). The generated worker C has precise root slots for all three values. On the ESP32-S3, the USB Serial/JTAG console delivered the final pass line when the monitor-attached reset began; the preceding run had already reported successful collection and join markers.

The [ESP32-S3 TCP socket fixture](../../../tests/embedded_gc_stage2_esp32_socket_buffer_device.bmx) holds a TCP server socket and a one-byte `MemAlloc` destination open while a managed worker blocks in `recv_`. The owner collects after 20 ms, requires completion within 300 ms, then sends a byte, joins the worker and verifies the received byte plus the worker's Object, Array and dynamically allocated String. The release `-gc-multicore` image passed repeatedly with a 128 KiB SRAM heap; see the [device log](multicore_native_boundary_esp32s3_socket_buffer.log). A 64 KiB image could not complete `BRL.Socket` module initialization because a String allocation failed, before the test began. The larger heap isolates the socket boundary check from that startup footprint.
